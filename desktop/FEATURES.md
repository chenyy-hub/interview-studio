## 系统音频：这次查到的事实

参考 App 的桌面层使用 Electron `desktopCapturer.getSources` 选择屏幕源，
在 `setDisplayMediaRequestHandler` 中，为请求音频的采集返回 `audio: loopback`。
macOS 启动参数包含 `MacLoopbackAudioForScreenShare` 与
`MacSckSystemAudioLoopbackOverride`。这是系统回环采集的证据；
没有在这条桌面采集路径观察到飞书或腾讯会议专用的内部接口。
这不等同于已经证明所有设备、会议版本都不会发生音频冲突。

我们的实际运行包基于官方 Pika 3.4.0 arm64，已有 Core Audio Tap 与
ScreenCaptureKit 原生后端。新增中文采音配置默认选择 ScreenCaptureKit，
麦克风默认关闭。仅系统音频模式不请求麦克风权限，不打开原生麦克风，
也不启动用户一侧的语音识别流。需要记录自己的发言时，可明确勾选麦克风。

程序仅保存要监听的设备标识，不修改系统默认播放/录音设备，不设置设备
hog mode，也不修改飞书、腾讯会议的设备设置。Tap 模式中的私有聚合设备
属于采集实现，不能把其“私有”或进程筛选参数误解为系统设备独占模式。
系统混音包含其他软件播放的声音；指定 Tap 输出设备时应与会议播放设备一致。

修复了原生采样率 API 名称不匹配：实际接口为 `getSampleRate`，旧封装
尝试读取 `get_sample_rate`，可能一直使用默认采样率。修复已用运行包测试。

仍需验证：飞书和腾讯会议实际通话时的双方听感、蓝牙耳机设备切换、
采集丢帧、长时间稳定性、权限拒绝后恢复、语音服务端的实时识别效果。
目前没有真实 CER/WER、转写端到端延迟或会议共存测试结果。

## 已做的验证

40 项 Node 测试与 4 项 Python 打包检查通过；运行包中的 SQLite、PDF、
DOCX、WebSocket 依赖和原生音频模块装载通过。真实运行包的麦克风延迟
打开、采样率读取、仅系统音频/可选麦克风启动分支使用合成数据验证。

最终 v0.4 已实际打开，确认中文服务配置页、默认系统音频与关闭麦克风、
缺少转写配置时的启动拦截、高级模型设置直接定位。设备枚举在本机未成功，
已隔离为独立进程且超时返回，界面仍可操作，默认设备选项仍可使用。
不能把这个结果写成“具体设备列表已验证”。

退出后检查到 Chromium 启动锁已消失，再次启动成功，最终停在中文服务配置页。
没有输入系统密码，没有填写或调用真实 API Key，也没有开启真实录音。
没有把模块装载、配置存在或模拟通过说成实际录音成功。

v0.5 已实际打开新增的回复速度、窗口与共享保护和双端互联页面，确认默认
单栏快答、系统保护请求与快捷键注册状态。退出后启动锁已释放。打包内
配对服务在 127.0.0.1 上通过错误令牌、单客户端限制、手机提问传递及
重连回答快照检查；这不代表已验证手机 Wi-Fi / 防火墙环境。

v0.6 将常用侧栏收拢为六项，设置内折叠高级选项，新增启动前数据源选择、
截图并提问和重新生成。真实打包 CredentialsManager 使用合成密钥验证
